# Итерация 6 — Миграция на Oban

Статус: **завершено**

## Отчёт о выполнении

* Добавлена зависимость `{:oban, "~> 2.19"}` (зафиксирована на 2.23.1), миграция `20260819000000_add_oban_jobs_table.exs` (`Oban.Migration.up(version: 14)`). Oban Web не подключён — по открытому вопросу итерации решено ограничиться `Oban` + observability через `mix ecto`/логи/телеметрию, UI можно добавить отдельно позже без миграции данных.
* **Ключевой риск итерации (порядок публикации per `partition_key`) решён без Oban Pro**: `ElixirChat.Workers.PublishOutboxEvent` (`lib/elixir_chat/workers/publish_outbox_event.ex`) — очередь `:outbox` с параллелизмом 10 (а не 1: раньше это было честно последовательно, т.к. был единственный GenServer-диспетчер — теперь разные партиции публикуются параллельно, что даже быстрее старого поведения). Перед публикацией джоба выполняется тот же самый `NOT EXISTS earlier unpublished` запрос, что раньше был частью `FOR UPDATE SKIP LOCKED`-claim; если находится более ранее неопубликованное событие той же партиции — джоб возвращает `{:snooze, 1}` (переставляется на выполнение через 1с, **не тратя** попытку из `max_attempts`), вместо публикации не по порядку. Так порядок гарантирован per-partition, при этом независимые партиции публикуются конкурентно.
* Durability для outbox-публикации спроектирована так, чтобы не деградировать по сравнению со старым поведением "ретраить бесконечно с capped backoff": `max_attempts: 1_000_000` (фактически бесконечно) + собственный `backoff/1` (та же формула `min(2^(N-1), 60)` секунд, что была в `OutboxDispatcher`), плюс однократный `Logger.warning` + телеметрия `[:elixir_chat, :outbox, :retry_exhausted]` после 10-й попытки — ровно как раньше, только источник счётчика попыток теперь `Oban.Job.attempt`, а не собственная колонка.
* `ElixirChat.Workers.DeliverPushNotification` (`lib/elixir_chat/workers/deliver_push_notification.ex`) — очередь `:push`, параллелизм 8 (было: `Task.async_stream` max_concurrency 8). В отличие от outbox, push — best-effort и должен сдаваться: `max_attempts: 10`, на последней неудачной попытке (`attempt >= max_attempts`) джоб сам удаляет `push_delivery`-строку через новую `Notifications.discard_delivery/2` и шлёт ту же телеметрию `[:elixir_chat, :push, :retry_exhausted]`, что и раньше.
* **Jobs создаются в той же транзакции, что и бизнес-событие** (обязательное требование итерации): в `persist_message_transaction/4`, `edit_message/2`, `delete_message/2` (`lib/elixir_chat/chat.ex`) — `Multi.run(:publish_outbox_event_job, fn _repo, changes -> Oban.insert(PublishOutboxEvent.new(%{event_id: event.id})) end)` сразу после `Multi.insert(:outbox_event, ...)`, внутри того же `Ecto.Multi`/транзакции — если транзакция не закоммитится, джоба не будет вообще, и наоборот. `ElixirChat.OutboxDispatcher.wake_up()` (ручной "разбуди диспетчера" сигнал) убран полностью — Oban's insert-trigger (`LISTEN`/`NOTIFY`) даёт мгновенный подхват джобы без отдельного сигнала, что даже надёжнее старого двухэтапного "запись + отдельный wake_up".
* Та же атомарность применена и к push-джобам: `ElixirChat.Notifications.insert_deliveries_with_jobs/1` (`lib/elixir_chat/notifications.ex`) оборачивает `Repo.insert_all(PushDelivery, ..., on_conflict: :nothing, returning: [:id])` и `Oban.insert_all(jobs)` (по одному джобу на реально вставленную — не задедупленную `on_conflict`-ом — строку) в один `Repo.transaction`. `ElixirChat.NotificationSender.wake_up()` тоже убран по той же причине.
* `ElixirChat.OutboxDispatcher` и `ElixirChat.NotificationSender` (оба poll-GenServer'а) удалены полностью вместе со своим тестом (`outbox_dispatcher_test.exs`) — заменены на воркеры + новые тесты (см. ниже). `lib/elixir_chat/application.ex` — вместо двух GenServer'ов один `{Oban, Application.fetch_env!(:elixir_chat, Oban)}`.
* Ручные колонки-дублёры retry-состояния убраны: миграция `20260819000100_drop_manual_retry_columns.exs` удаляет `attempt_count`/`available_at`/`last_error` из `outbox_events` и `push_deliveries` — это состояние теперь единолично хранит `oban_jobs` (attempt/errors/scheduled_at/state), а не два параллельных источника истины. `ElixirChat.Chat.Outbox.event_changeset/3` и обе схемы (`OutboxEvent`, `PushDelivery`) обновлены соответственно. `Notifications.retry_delivery/2` упростился до одной строки (`:retry`, без мутации строки — Oban сам планирует следующую попытку); добавлена `Notifications.discard_delivery/2` (замена решения "10 попыток → удалить + телеметрия", раньше жившего в `retry_delivery/2`).
* **Тестовый режим — `testing: :inline`** (`config/test.exs`), а не рекомендованный по умолчанию Oban-guide `:manual`: `:inline` выполняет `perform/1` синхронно, в том числе внутри `Ecto.Multi` (после коммита оборачивающей транзакции) — то есть даёт ровно то же "нет отдельного поллера, с которым можно словить гонку", что раньше давал `synchronous_wake_up: true` у `OutboxDispatcher.dispatch_now`. Выбрано намеренно вместо `:manual`, чтобы не переписывать все ~180 существующих тестов (`chat_test.exs`, `chat_live_test.exs`, `notifications_test.exs`), которые полагаются на синхронную доставку сразу после `Chat.create_message`, — эмпирически подтверждено прогоном полного `mix test`.
* Три существующих теста в `notifications_test.exs` обновлены под новую механику "enqueue теперь синхронно доставляет" (раньше `Notifications.process/2` только ставил в очередь, доставка была отдельным шагом через `ElixirChat.NotificationSender.dispatch_now()`, которого больше нет): убраны вызовы `dispatch_now()` (доставка уже произошла к моменту возврата из `process/2`), тест на "временный сбой" переименован и переписан под факт, что строка `push_delivery` просто остаётся в базе (нет больше `attempt_count`/`last_error` для проверки), тест на "перенос браузера между аккаунтами" адаптирован так, чтобы доставка не успевала удалить строку раньше проверки переноса (сбой теперь намеренно retryable).

### Известные ограничения (осознанно отложено)

* **Retention/cleanup outbox_events/push_deliveries/oban_jobs не реализован в этой итерации** — старый `OutboxDispatcher.delete_expired/1` (retention 7 дней после `published_at`) убран вместе с диспетчером и ничем не заменён; `Oban.Plugins.Pruner`/`Oban.Plugins.Cron` тоже не подключены. Это осознанно и по плану: Итерация 7 ("Retention/cleanup + сквозные regression-тесты") в дорожной карте явно владеет этим — добавлять его здесь означало бы забегать вперёд и дублировать будущую работу. Между итерациями 6 и 7 `outbox_events`/`push_deliveries`/`oban_jobs` растут без границ — не проблема для функциональности, но отслеживается как известный временный пробел.
* Oban Web не подключён (открытый вопрос итерации решён в пользу "не сейчас") — наблюдаемость пока только через `mix ecto`/логи/существующую телеметрию; добавляется отдельно без миграции данных, если понадобится.
* Тестовый режим `:inline` — осознанное отклонение от рекомендованного Oban-guide'ом по умолчанию `:manual`, ради нулевых изменений в ~180 существующих тестах; недостаток — реальные джобы никогда не попадают в `oban_jobs` во время обычных тестов (только в `oban_durability_test.exs`, который явно переключается на `:manual`), поэтому `assert_enqueued`/`all_enqueued` в основной массе тестов не сработают без такого явного переключения — задокументировано прямо в модуле теста.
* Очередь `:outbox` с параллелизмом 10 (не 1) — сознательный выбор поверх snooze-based упорядочивания: разные партиции публикуются конкурентно (быстрее старого полностью последовательного диспетчера), при этом порядок **внутри** одной партиции гарантирован независимо от параллелизма очереди.

## Текущее состояние (то, что заменяется)

Два самодельных poll-GenServer, оба уже DB-backed и переживают рестарт:
* `ElixirChat.OutboxDispatcher` (`lib/elixir_chat/outbox_dispatcher.ex`) — публикует `outbox_events` (poll 1с/`wake_up`, `FOR UPDATE SKIP LOCKED` per `partition_key`, retry с backoff до 60с, retention 7 дней после публикации, telemetry `retry_exhausted` после 10 попыток).
* `ElixirChat.NotificationSender` (`lib/elixir_chat/notification_sender.ex`) — доставляет `push_deliveries` (poll 1с, `Task.async_stream` max_concurrency 8, retry с backoff cap 300с, discard после 10 попыток).

Оба уже дают at-least-once + durability через рестарт — миграция на Oban не чинит "потерю данных" (её и так нет), а даёт: единый стандартный API retry/backoff, Oban Web/UI для наблюдения, `Oban.Plugins.Cron` для cleanup-джобов (нужны в Итерации 7), встроенный dead-letter/discarded-статус вместо ручного `last_error`-поля, меньше самодельного кода для поддержки.

## Открытые вопросы для уточнения перед стартом

* Ordering per `partition_key`: Oban из коробки не гарантирует строгий порядок обработки в рамках произвольного ключа так же прямолинейно, как текущий ручной `FOR UPDATE SKIP LOCKED`-claim по `partition_key` — нужно явно продумать (Oban unique jobs + queue concurrency = 1 для этой очереди, либо `Oban.Pro`-фичи, если доступны, либо оставить claim-логику поверх Oban-воркера). Это ключевой риск итерации, требует отдельного мини-исследования Context7/Oban docs перед реализацией.
* Нужен ли Oban Web (доп. зависимость, доп. UI) сразу, или ограничиться `Oban` + `Oban.Plugins.Cron` без веб-интерфейса на этом этапе?
