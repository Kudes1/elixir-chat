# Итерация 4 — Разбор @mention, durable Notification, сужение push

Статус: **завершено**

## Отчёт о выполнении

* `ElixirChat.Chat.Mentions` (`lib/elixir_chat/chat/mentions.ex`) — единственное место, определяющее синтаксис `@login`: `fragments/1` (для рендера — `{:text, ...}`/`{:mention, ...}` пары) и `logins/1` (уникальные логины без `@`, в порядке первого упоминания, для резолва на бэкенде). `ElixirChatWeb.ChatLive.Components.mention_fragments/1` теперь просто делегирует в этот модуль — тот же regex, что раньше жил только в компоненте рендера, больше не может разойтись со серверным парсером, потому что это буквально один и тот же код, а не две синхронизируемые копии.
* Новая durable-сущность `ElixirChat.Notifications.Notification` (`lib/elixir_chat/notifications/notification.ex`, миграция `20260818000000_add_notifications.exs`, таблица `notifications`, `unique_index([:message_id, :recipient_id, :type])`) — источник истины "этому получателю нужно знать про это сообщение", отдельно от `push_deliveries` (которые остаются записью попытки доставки по одному транспорту, не источником истины). Типы ограничены реально существующими в проекте: `"mention"` и `"direct_message"` — тредов и реакций в проекте нет, эти типы не изобретались заранее.
* `ElixirChat.Chat.persist_message_transaction/4` — новый шаг `Multi.run(:notifications, ...)`, срабатывающий только когда сообщение реально создано (не на идемпотентном повторе — совпадает с тем, как уже ведёт себя шаг `:outbox_event`):
  * Для канала (`direct_info == nil`): `Mentions.logins/1` по телу сообщения; если пусто — ни одного запроса, ни одной строки (важно для бюджета SQL-телеметрии, см. тесты); иначе резолв логинов в `user_id` пересечением с `conversation_user_ids(channel.id) -- [author]` (тот же helper, что уже используется для push и unread) — упоминание себя или несуществующего логина резолвится в ничто, а не в ошибку.
  * Для DM (`direct_info` есть): всегда ровно одна `Notification` типа `"direct_message"` для второго участника — DM и сегодня безусловно важен, поведение не меняется, просто теперь материализовано как durable-строка, а не только как push-путь.
  * `insert_all` с `on_conflict: :nothing` по тому же уникальному индексу — повторная доставка (идемпотентный ретрай сообщения) безопасна и не дублирует уведомления.
* `ElixirChat.Notifications.process(:channel, message)` — узкое место сужения push: вместо `Chat.conversation_user_ids(...) -- [author]` (все участники канала) теперь читает получателей из только что вставленных `Notification` строк типа `"mention"`. Контрольный сценарий из заметок пользователя закрыт: обычное сообщение в канал на 200+ участников — 0 `Notification`, 0 `push_deliveries`, а не 199. `process(:direct, ...)` не менялся — он и раньше был узким (один конкретный собеседник).
* `ElixirChatWeb.ChatLive` (`maybe_notify_channel_message/2`, `maybe_notify_direct_message/4`, `push_notify/3`) — `priority` для клиентского `NotificationPolicy` теперь тоже резолвится на сервере через `Notifications.mentioned?/2`, а не выводится клиентом из `type` (`"direct" → high`, как было временным решением Итерации 3): DM — всегда `"high"`; обычное сообщение канала — `"high"`, если конкретно этот получатель был `@mention`-нут, иначе `"low"`. Разным получателям одного и того же сообщения канала может достаться разный `priority` — ровно то, что раньше нельзя было различить, потому что решение принималось по общему для всех `type`. `assets/js/app.js` — слушатель `phx:notify` читает `detail.priority` напрямую вместо вывода из `type`; `notification_policy.js` не менялся (входной контракт `priority: "high"|"low"` не поменялся, поменялся только источник значения).
* `ElixirChat.Notifications.read_at/1` — минимальный, осознанно нестандартный `read_at`: не отдельная колонка/запись, а вычисление по уже существующему `conversation_reads` (`ElixirChat.Chat.upsert_read_cursor/5` остаётся единственным местом записи курсора; дублирующий путь записи только развёл бы два источника истины). `nil`, если ещё не прочитано. `seen_at` не введён вовсе — в проекте до сих пор нет отдельного UI "центра уведомлений", который был бы его потребителем (см. открытый вопрос итерации ниже), поэтому сущность без потребителя сознательно не изобретена — так же, как это было решено для `seen_at` заранее в самой итерации.

### Известные ограничения (осознанно отложено)

* `seen_at` не введён — по условию самой итерации, до появления отдельного UI "центра уведомлений", который был бы его потребителем; тредов/реакций в проекте до сих пор нет, поэтому новые типы `Notification` под них не заводились.
* `received_at`/ACK-инфраструктура из формулировки цели итерации не реализованы: в проекте нет отдельного клиентского ACK-протокола для *конкретного факта получения одного сообщения* (в отличие от уже существующего per-partition `event_seq`-курсора из Итерации 1, который про "докуда докатился разрыв", а не про доставку одной сущности) — вводить `received_at` без единственного правдоподобного источника его значения означало бы изобретать семантику, а не документировать существующую. При появлении такого источника (например, если Итерация 5+ введёт явный ACK на уровне сообщения) поле добавляется без риска для существующих данных — обычной `add`-миграцией на уже существующую таблицу.
* Резолв `@mention` ограничен группами (`direct_info == nil`); для DM `@login` продолжает быть чисто визуальной подсветкой без второго уведомления — DM и так уже безусловно уведомляет единственного собеседника, дополнительный `Notification` типа `"mention"` внутри DM ничего нового не добавил бы.
* `Mentions.logins/1` не проверяет, что упомянутый логин соответствует реальному текущему участнику именно этого канала на регулярном выражении — это делает отдельный SQL-запрос в `Chat.insert_notifications/5` (пересечение с `conversation_user_ids/1`), сознательно: сам парсер синтаксиса не должен знать о базе данных.

См. общий контекст в `tasks/00-roadmap.md`. Соответствует "Этапам 8-9" в `tasks/plan and checklist.md`.

## Проблема сегодня (уже воспроизводима, не гипотетическая)

`ElixirChat.Notifications.enqueue/2,3` (`lib/elixir_chat/notifications.ex`) создаёт `push_deliveries` для **каждого** получателя на **каждое** сообщение (канал или DM), если получатель не замьютил канал/всё глобально. Разбора `@mention` на бэкенде нет вообще — сегодня `@mention` это чисто UI: автокомплит вставки текста (`insert_mention` в `chat_live.ex:431`) и подсветка уже введённого `@login` при рендере (`mention_fragments/1`, `lib/elixir_chat_web/live/chat_live/components.ex:879`). Никакой связи с конкретным `user_id` для нотификации нет.

Контрольный тест из заметок пользователя воспроизводим уже сейчас: канал на 200 участников → 1 обычное сообщение → сегодня это до 199 `push_deliveries` строк и push-уведомлений всем.

## Цель

* Реальный разбор `@login` в теле сообщения на бэкенде при создании сообщения (`persist_message_transaction/4`, `chat.ex:771`), резолв в конкретные `user_id` среди участников канала.
* Ввести durable-сущность **Notification** (отдельно от `push_deliveries`, которые становятся записью попытки доставки, а не источником истины) — как минимум для типов: mention, direct message (DM уже фактически "важен" и сегодня); thread reply/invite — только если/когда в проекте появятся треды (сейчас в проекте **нет тредов и нет реакций** — не изобретать эти типы заранее, ограничиться реально существующими: mention, DM).
* Создавать `Notification` атомарно вместе с сообщением через тот же `Ecto.Multi`, что уже используется в `persist_message_transaction/4`.
* Обычное сообщение канала **не** создаёт `Notification`/`push_delivery` для рядовых участников — только для тех, кого явно `@mention`-нули, плюс DM всегда (согласно текущей политике).
* Добавить `received_at` (= ACK/доставлено, из будущей ACK-инфраструктуры или из факта применения на клиенте), `seen_at` (пользователь увидел в UI/центре уведомлений — если такой появится), `read_at` (сообщение/тред открыт) — если для этой итерации центра уведомлений ещё нет, минимально ввести хотя бы `read_at` через существующий `conversation_reads` (уже фактически "read"), а `seen_at` отложить до появления отдельного UI для уведомлений (не изобретать сущность без потребителя).
