# Итерация 3 — NotificationPolicy + первая версия звука/toast/badge

Статус: **завершено**

## Отчёт о выполнении

* `assets/js/notification_policy.js` — чистый модуль `decide(input)` без DOM/LiveSocket-зависимостей: вход `{connectionState, own, muted, active, tabVisible, tabFocused, priority}`, выход `silent | badge | toast | sound`. Правила: не-`live` состояние → `silent`; собственное сообщение → `silent`; замьюченный канал/DM → `silent`; если получатель уже смотрит именно в этот канал/DM и вкладка видима и в фокусе — событие подавляется (`silent` для обычных сообщений, `badge` для DM); если вкладка не видна/не в фокусе — DM даёт `sound`, обычное сообщение — `badge`; иначе (вкладка активна, но не тот диалог открыт) — DM даёт `toast`, обычное сообщение — `badge`. Никакой код обработки события в `chat_live.ex` или JS не вызывает звук/toast напрямую — всегда через эту функцию.
* `assets/js/notification_policy.test.mjs` — юнит-тесты через встроенный `node --test` (без новых npm-зависимостей: в проекте по-прежнему нет JS-тест-раннера, но Node уже содержит один "из коробки"). 9 тестов, ровно таблица случаев из `tasks/00-roadmap.md`/итерации: catching_up/connecting/disconnected → silent, own → silent, muted → silent, обычное сообщение при открытой активной вкладке → badge, DM не в фокусе → sound, DM активного диалога → сведено к badge/sound по фокусу. Запуск: `node --test assets/js/notification_policy.test.mjs`.
* `assets/js/notification_ui.js` — DOM-часть, отделённая от чистой логики: `showToast({title, senderName, preview})` (один компонент, до 3 одновременных тостов, автозакрытие через 5с, клик закрывает раньше) и `playNotificationSound()` (один короткий синтезированный сигнал через Web Audio API `OscillatorNode` — сознательно без бинарного аудио-файла, чтобы не тащить в репозиторий лицензируемый ассет и не решать вопрос его прав; best-effort, ошибки проигрывания проглатываются).
* `assets/css/app.css` — стили `#orbit-toast-container`/`.orbit-toast` на существующих `--orbit-*` токенах темы (шэлл чата всегда тёмный, отдельного light-варианта переменных нет — см. существующий код), `z-index: 70` (выше `.channel-modal-backdrop` с `z-index: 60`).
* `assets/js/app.js` — импортирует `decide`/`showToast`/`playNotificationSound`; слушатель `phx:notify` собирает единственные по-настоящему клиентские сигналы (`connectionState.current`, `document.visibilityState`, `document.hasFocus()`) и решает `toast`/`sound` — `active`/`title`/`sender_name`/`preview` уже приходят готовыми от сервера. Хук `ConnectionState` при разрешении `CATCHING_UP → LIVE` (микротаск) теперь ещё и шлёт `pushEvent("client_caught_up", {})` на сервер.
* `lib/elixir_chat_web/live/chat_live.ex`:
  * Новый `handle_event("client_caught_up", ...)` переводит `@connection_state` из `:catching_up` в `:live` через `ConnectionState.transition/2` (закрывает найденный при разработке пробел: без этого `@connection_state`, единожды выставленный в `mount/3`, никогда не обновлялся дальше в течение жизни законнекченного процесса — после реального catch-up все последующие live-события в течение всей сессии считались бы "во время catch-up" и оставались бы немыми навсегда).
  * `handle_info({:conversation_message_created, ...})` и `handle_info({:direct_message_created, ...})` — единственные два места, откуда шлётся `push_event(socket, "notify", ...)` (оба файрят ровно один раз на получателя на сообщение, независимо от того, открыт ли сейчас этот канал/DM — то есть корректная точка для решения о нотификации, без дублирования с `{:message_created, ...}`/`{:direct_message_updated, ...}`, которые обновляют только открытое окно сообщений).

  * `maybe_notify_channel_message/2`, `maybe_notify_direct_message/4` — формируют `active`/`title` **на сервере** (сервер уже знает, открыт ли этот канал/DM у сокета — `@channel`/`@direct_conversation`), поэтому клиенту остаётся решать только то, что реально знает только браузер (видимость вкладки, фокус, актуальное состояние соединения).
* Тесты: `test/elixir_chat_web/live/chat_live_test.exs` — 6 новых интеграционных тестов через `assert_push_event`/`refute_push_event`: notify для чужого сообщения в неоткрытом канале, `active: true` когда канал открыт, отсутствие push для собственного сообщения, отсутствие push для замьюченного канала, push для DM с именем собеседника в заголовке, и главный сценарий — во время `catching_up` push подавлен, после `render_hook(view, "client_caught_up", %{})` состояние переходит в `live` и следующее сообщение уже даёт `notify`.

### Известные ограничения (осознанно отложено)
* Разбора `@mention` на бэкенде всё ещё нет — «обычное сообщение» трактуется как единственный `low`-приоритет; полноценная градация `mention/DM/обычное` — Итерация 4.
* Cooldown/группировка звуков (например, серия сообщений в разных каналах подряд) не реализованы — сознательно отложено в Итерацию 5.
* Browser Notification API (уведомление вне вкладки из самой вкладки, не через Service Worker) не реализован — решено не делать, так как Web Push уже закрывает этот сценарий отдельным транспортом; при необходимости добавляется как ещё один уровень в `notification_ui.js`, не меняя `notification_policy.js`.
* Звук — синтезированный тон через Web Audio API, а не файл-ассет; если позже понадобится другой/брендированный звук, проще всего заменить содержимое `playNotificationSound()` на воспроизведение `<audio>`, не трогая вызывающий код.
* JS-тесты запускаются вручную (`node --test`) — не подключены к `mix test`/CI-пайплайну; это осознанно, т.к. Elixir и JS тесты в проекте выполняются раздельно (нет единого раннера), а `mix precommit`/`mix test` покрывают всё остальное.

См. общий контекст в `tasks/00-roadmap.md`. Соответствует "Этапам 6-7" в `tasks/plan and checklist.md`.

## Цель

Сегодня в приложении **нет вообще никакого звука/toast/browser-notification для чат-событий** (проверено: ни `Audio()`, ни `new Notification()` в JS, только `showNotification` внутри `sw.js` для Web Push). Это значит фичу можно построить сразу правильно — с `NotificationPolicy`, отделённым от транспорта, а не чинить существующий спам. Главный acceptance-критерий по заметкам пользователя: **события, применённые во время `CATCHING_UP`, обновляют UI, но никогда не создают звук/toast; звук/toast возможны только для событий, пришедших после перехода в `LIVE`.**

## Задачи

* Ввести `NotificationPolicy` как отдельный модуль (вероятно JS-модуль, т.к. решение "играть звук/показать toast" — клиентское), принимающий на вход как минимум: текущее состояние клиента (`LIVE`/`CATCHING_UP`/...), тип события, отправитель ли это сам пользователь, открыт ли сейчас нужный канал/DM, активна ли вкладка (`document.visibilityState`/`document.hasFocus()`), настройки пользователя (пока минимально — заглушка/на основе уже существующих `NotificationPreference` per-channel mute).
* Никакой код обработки события (`handle_info` в `chat_live.ex`, JS-обработчики) не должен напрямую вызывать проигрывание звука — только через `NotificationPolicy`.
* Минимальный набор решений на первой итерации: `silent | badge | toast | sound` (browser notification из вкладки — не обязателен в этой итерации, т.к. Web Push уже закрывает "уведомление вне вкладки"; решить на месте, не обязательно делать сразу оба канала).
* Один звуковой файл, один toast-компонент — не усложнять раньше времени (cooldown/группировка — отдельная Итерация 5).
